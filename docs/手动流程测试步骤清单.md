# CCNC 手动流程测试步骤清单

> 用途：浏览器 + 管理端界面手工回归（可与 API/脚本验证互补）  
> 环境：PostgreSQL `5432` / Redis `6380` / 后端 `http://localhost:3000`  
> 前端：H5 `http://localhost:5174` / 管理端 `http://localhost:5173`（以实际启动端口为准）  
> 账号：`admin/123456`｜`testuser/123456`｜`promoter/123456`（邀请码 `PROMO001`）

---

## 使用说明

1. 按章节顺序执行；每步完成后在「结果」列勾选或填写实际现象。
2. 需要改库/等 cron 的步骤，已注明备用操作。
3. **直推分润受邀请解锁影响**：推广员有效邀请不足 1 人时，一级分润金额可能为 0（不生成记录）。建议用**新注册下线的首投**来产生分润。
4. 管理端登录 token 在响应顶层字段 `token`（不是 `data.access_token`）。

## C. 充值 → 下单 → 支付（产生 PENDING 分润）

| # | 步骤 | 操作 | 预期 | 结果 |
|---|------|------|------|------|
| C1 | 下线实名 | 新用户登录 → 提交实名（姓名 + 18 位身份证号） | 实名状态为已通过 | ☐ |
| C2 | 充值/调账 | H5 充值走通；或管理端对该用户余额调账（如 +5000） | 余额足够下单（≥ 产品最低额，默认 1000） | ☐ |
| C3 | 记录推广员余额 | 用 `promoter` 登录，记下当前可用余额 | 作为对照基数 | ☐ |
| C4 | 下单并余额支付 | 新用户：选产品 → 下单 → 余额支付 1000 | 订单变为进行中（`ACTIVE`） | ☐ |
| C5 | 查分润记录 | 管理端 **佣金管理**；或推广员 H5 **收益明细** | 出现 **待结算（PENDING）** 分润；金额 = 本金 × 直推比例 × 解锁比例（例：1000×5%×1/3≈16.67） | ☐ |
| C6 | 确认未提前入账 | 再看 `promoter` 余额 / 钱包流水 | 支付瞬间**不应**因分润增加余额 | ☐ |

> 若 C5 无分润：检查推广员解锁比例是否为 0、下线是否已绑定、订单是否支付成功。

## D. 订单到期结算（本金 + 收益）

| # | 步骤 | 操作 | 预期 | 结果 |
|---|------|------|------|------|
| D1 | 制造到期 | DB 将该 `ACTIVE` 订单的 `end_date` 改为过去时间；记下买家当前余额 | 订单满足到期条件 | ☐ |
| D2 | 等待订单 cron | 等待约 **1 分钟**（每分钟任务） | 订单状态 → **已结算 / SETTLED**；买家余额增加 **本金 + 收益** | ☐ |
| D3 | 确认分润仍待结算 | 管理端 / H5 收益明细 | 对应分润仍为 **待结算 PENDING**（尚未发放） | ☐ |

---

## E. 分润结算发放（PENDING → SETTLED → PAID）

| # | 步骤 | 操作 | 预期 | 结果 |
|---|------|------|------|------|
| E1 | 记下推广员余额 | `promoter` 可用余额 | 对照基数 | ☐ |
| E2 | 手动触发结算 | 管理端触发，或 Swagger/接口：`POST /api/v1/admin/commissions/run-settlement`（Bearer admin token） | 返回类似 `{"settled":N,"paid":M}`，N/M ≥ 1 | ☐ |
| E3 | 状态流转 | 查该分润详情/列表 | 变为 **已发放 PAID**；库中有 `settled_at`、`paid_at` | ☐ |
| E4 | 钱包入账 | 推广员余额与流水 | 余额增加 = 分润金额；流水 `reference_type=COMMISSION` | ☐ |
| E5 | 幂等 | 再次执行 `run-settlement` | `settled=0, paid=0`；余额不再增加 | ☐ |
| E6 | Cron 观察（可选） | 观察后端日志约 5 分钟 | 出现 `job:commission-settlement finished` 或等价结算日志 | ☐ |

## H. 边界与异常（管理端）

| # | 场景 | 操作 | 预期 | 结果 |
|---|------|------|------|------|
| H1 | 订单未 SETTLED | 仅有 `ACTIVE` 订单的 PENDING 分润时点「执行结算」 | 不标记 SETTLED、不发放 | ☐ |
| H2 | 延迟天数 | 规则 `settle_delay_days>0`，订单刚 SETTLED | 未到延迟日不结算；改回 0 后可结算 | ☐ |
| H3 | 退款作废 | 对仍为 `ACTIVE` 且已有 PENDING 分润的订单做**管理员退款** | 分润 → `VOID`；不会再发放 | ☐ |
| H4 | 冻结/解冻 | 佣金详情：冻结 → 解冻 | 冻结期间不发放；解冻回 `SETTLED` 或 `PENDING` | ☐ |
| H5 | 人工补发 | 管理端人工补发 / `POST .../manual-credit` | 最终 `PAID`，余额增加对应金额 | ☐ |

> 注意：当前退款接口仅接受订单状态 `ACTIVE` 或 `PAID`，**已 SETTLED 订单不能走退款接口**；已 SETTLED 的 PENDING 分润可用管理端「作废」处理。

### PowerShell 触发结算示例

```powershell
$login = Invoke-RestMethod -Uri "http://localhost:3000/api/v1/admin/auth/login" `
  -Method POST -ContentType "application/json" `
  -Body '{"username":"admin","password":"123456"}'
$token = $login.token
$headers = @{ Authorization = "Bearer $token" }

Invoke-RestMethod -Uri "http://localhost:3000/api/v1/admin/commissions/run-settlement" `
  -Method POST -Headers $headers
```

### 数据库快速核对

```sql
SELECT status, COUNT(*) AS cnt FROM commissions GROUP BY status;

SELECT id, biz_id, to_user_id, amount, status, settled_at, paid_at
FROM commissions ORDER BY id DESC LIMIT 20;

SELECT id, user_id, status, amount, end_date FROM orders ORDER BY id DESC LIMIT 20;

SELECT * FROM wallet_logs
WHERE reference_type = 'COMMISSION'
ORDER BY id DESC LIMIT 20;
```

也可在 `service` 目录执行：

```bash
node scripts/check-commission.mjs
node scripts/check-order-commissions.mjs
```

### 已知注意点

1. 订单结算 cron **每 1 分钟**；分润结算 cron **每 5 分钟**（也可手动 `run-settlement`）。
2. 直推金额受 `invite_progress.unlock_ratio` 影响：0 / 1/3 / 2/3 / 1。
3. 若 3000 端口被旧进程占用，确认实际进程已加载最新代码后再测人工补发等接口。
4. 更完整的状态机与 API 说明见：[`验证流程清单.md`](./验证流程清单.md)。
